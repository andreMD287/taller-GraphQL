Ejercicio 1 — Query Básica

Tu primera consulta

1 Copia esto en el panel izquierdo
query { libros { titulo autor } }
2 Presiona ▶ Run
🎯 Objetivo: Entender que GraphQL devuelve exactamente los campos que pedimos.
✓ Resultado esperado
{ "data": { "libros": [ { "titulo": "El Problema de los Tres Cuerpos", "autor": "Liu Cixin" }, ... ] } }

💡 Nota: No importa cuántos campos tenga "Libro" en el servidor. Solo recibes lo que pides.

Ejercicio 2 — Flexibilidad

Agregando y quitando campos

query { libros { titulo autor paginas genero } }

Ahora pedimos 4 campos. Mismo endpoint, distinta respuesta.

query { libros { titulo } }

🔥 Mini reto: Modifica la query para pedir solo el campo id.

🎯 Objetivo: Demostrar que no existe versionamiento de API (nada de /v1/, /v2/). Evolucionas sin romper nada.
Ejercicio 3 — Argumentos

Filtrando datos desde el cliente

1 Copia y ejecuta
query { librosPorGenero(genero: TECNOLOGIA) { titulo autor } }
💡 ¿Qué pasó?

GraphQL permite pasar argumentos a cualquier campo. Es el equivalente a un filtro en REST, pero definido en el schema.

🔥 Mini reto: Cambia el género a CIENCIA_FICCION y observa la diferencia.

Ejercicio 4 — Mutation

Modificando datos

Query = Leer   |   Mutation = Escribir/Modificar

mutation { agregarLibro(input: { titulo: "Docker para Devs" autor: "Juan Pérez" paginas: 320 genero: TECNOLOGIA }) { id titulo } }
✓ Después de ejecutar

1. La mutation devuelve el id y titulo del nuevo libro.
2. Vuelve a la Query de todos los libros y verás el nuevo libro agregado.

🔥 Mini reto: Agrega un libro con tus datos ficticios.

Ejercicio 5 — Tiempo Real

Subscription (WebSocket)

GraphQL soporta tiempo real nativo sin polling.

1 Abre una nueva pestaña en el Sandbox
subscription { libroAgregado { id titulo autor } }
2 En la pestaña anterior

Ejecuta otra mutation para agregar un libro diferente.

Verás que la subscription recibe el nuevo libro instantáneamente.

🎯 Objetivo: Entender que GraphQL usa WebSocket para datos en tiempo real (chats, notificaciones, dashboards).
Ejercicio 6 — Introspection

El API se documenta solo

# Pregúntale al API qué tipos tiene { __schema { types { name } } }

Con Introspection, herramientas como Apollo Sandbox generan la documentación automáticamente.

No necesitas Swagger. El schema es la documentación.

⚠️ Errores Comunes

Qué NO hacer

❌ Pedir un campo que no existe en el schema

# "precio" no existe en Libro { libros { titulo precio } }

❌ Olvidar las llaves de cierre

{ libros { titulo }

❌ Usar mutation en una query

query { agregarLibro(...) }

✅ Recuerda: GraphQL siempre responde HTTP 200. Los errores vienen dentro del JSON, en el campo "errors".

Conexión con la materia

GraphQL en Sistemas Distribuidos

GraphQL actúa como middleware:
• Transparencia: El cliente no sabe que hay múltiples servicios detrás.
• Agregación: Una sola query puede unir datos de Users, Products y Notifications.
• Reducción de tráfico: Menos viajes de red. Sin over-fetching ni under-fetching.

GraphQL en 4 Ideas

El cliente controla la respuesta. Adiós over/under-fetching.
② Un solo endpoint
POST /graphql para leer, escribir y tiempo real.
③ Schema como contrato
Documentación viva. Equipos alineados.
④ Ideal para distribuir
Gateway que unifica microservicios heterogéneos.
